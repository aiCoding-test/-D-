# 05 模块拆分与风险

> 本文为设计阶段基线；实际实现与验证结果请参阅 [实现差异](09-实现差异与限制.md) 和 [验收记录](../evidence/acceptance.md)。

## 1. 模块边界与实现次序

模块是同一个代码仓库中的职责分层，不是拆成多个微服务。部署时只区分 API、Worker 和数据库。

| 模块 | 核心职责与输入输出 | 依赖 | 完成标志 |
| --- | --- | --- | --- |
| M1 领域与流程定义 | 固定 StepSpec、DAG 校验、状态转换、错误分类；输出冻结快照 | 无基础设施依赖 | 环/缺失依赖拒绝；流程有稳定版本 |
| M2 持久化与事务 | Task/Step/Attempt/Event/资源/缓存仓储、锁顺序、CAS、迁移 | M1、PostgreSQL | 状态和事件原子提交，关键唯一约束生效 |
| M3 提交与查询 API | 幂等接收、详情、历史、控制命令与受控下载 | M1、M2 | 重发同请求同任务；控制冲突可解释 |
| M4 Worker 协调器 | 依赖推进、候选选择、资源准入、Attempt 创建、完成汇总 | M1、M2 | 单步闭环后可执行完整 DAG |
| M5 执行监督器 | 子进程启动、进度接收、独立续约、退出/超时/取消处理 | M2、M4 | 计算挂起不阻断心跳与控制路径 |
| M6 恢复与重试 | 租约扫描、LOST、退避、失败收敛、人工恢复代次 | M2、M4、M5 | 杀 Worker 后只重做未完成步骤，迟到提交被拒绝 |
| M7 产物与缓存 | 私有目录、manifest、校验、不可变发布、正式引用、缓存键 | M1、M2 | 崩溃窗口可解释；无效文件不命中 |
| M8 资源管理 | CPU/模拟 GPU 槽位、原子绑定、隔离、采样适配 | M2、M5 | 排队不消耗 Attempt；隔离不会自动误释放 |
| M9 动画 MOCK 处理器 | 模拟耗时、阶段与帧进度、确定性产物、故障注入 | M1、M7 | 每步遵守同一输入输出与错误协议 |
| M10 看板与可观测查询 | 固定 DAG、时间线、日志关联、资源区与统计 | M3 | 刷新/重连后状态仍完整可读 |
| M11 验证与交付 | 数据库/进程故障验证、环境、演示、记录、公开仓库 | 全部 | 按 07 提供可复现证据，不把计划当成果 |

MOCK 的语义输出应由输入与有效参数确定；task_id、当前时间和故障计划只作为执行元数据，不混入可复用内容。故障注入策略按本代次 Attempt 序号执行，例如“首次失败”在第二次尝试成功，不能每次重启都重新触发首次失败。

建议执行顺序：M1/M2 → M3 最小接收查询 → M4/M5/M7 单步闭环 → M6 故障恢复 → 完整 M9 DAG → M8 资源场景 → M10 页面 → M11 回归交付。可观测字段与事件从第一条任务就加入，不能到最后才补日志。

## 2. 各模块需要额外注意的风险

| 模块 | 主要风险 | 具体约束 / 控制 | 对应验证 |
| --- | --- | --- | --- |
| 流程定义 | 代码升级后旧 Task 跑了新语义；依赖环导致永远等待 | 保存 DAG/处理器版本快照；缺失旧版本拒绝执行并给明确错误；创建前拓扑校验 | 恢复旧任务；非法图验证 |
| 事务层 | 双领取、死锁、状态与历史不一致 | 固定锁顺序、短事务、部分唯一约束、受 token 保护的更新；冲突重读 | 两 Worker 争抢、取消/完成竞争 |
| API | 响应丢失导致重复任务；旧页面重复恢复 | 请求指纹、唯一幂等键、命令收据、控制 revision | 并发同键创建与超时重发 |
| 协调器 | 只靠一次回调推进导致重启后 DAG 卡住 | 所有待推进条件可由 DB 扫描重建，推进幂等 | 成功提交后立刻杀进程 |
| 监督器 | 计算占满线程，心跳中断；管道阻塞；子进程遗留 | 计算子进程隔离、输出限速/有界缓冲、独立控制循环；明确容器故障边界 | 挂起执行器与杀容器 |
| 恢复器 | 误把慢任务当死任务；旧 Worker 回来覆盖新结果 | 租约与业务超时分离；过期不可续活；CAS/fence；隔离旧资源 | 心跳存活长执行、迟到回报 |
| 重试 | 永久错误反复烧 GPU；重启把预算清零 | 错误分类、本代次尝试预算、持久 next_run_at | 稳定 OOM、重启退避 |
| 产物 | 半文件被下游读取；先写 DB 后文件丢失 | 私有目录、完整校验、先文件后引用、不可变路径；明确孤立文件窗口 | 三个提交边界的故障注入 |
| 缓存 | 参数/模型漏进 key；MOCK 污染真实结果；丢文件仍命中 | 规范化语义键、版本与种子、模拟模式、命中前校验 | 改种子/编码/模型、删文件 |
| 资源 | 同 GPU 双分配；租约过期但旧内核仍运行 | 同事务绑定；QUARANTINED；确认停止后释放；MVP 独占整卡 | 并发排队、失联隔离 |
| MOCK | 随机失败不可复现；模拟界面让人误以为真 GPU | 固定故障计划、显式模拟标记、真实资源与模拟指标分栏 | 同一计划重复运行 |
| 页面 | 把过期数据当实时；Step 失败被任务成功遮盖 | 显示更新时间、Attempt 历史、错误与数据源；后端校验按钮动作 | 断网、刷新、重试成功后历史 |
| 交付 | 文档承诺多于实现；仓库有密钥或不可复现依赖 | 完成状态表、锁版本、示例配置、全新环境启动与公开可读检查 | 发布前自查及证据记录 |

## 3. 最需要优先解决的五个问题

1. **状态所有权**：锁只保护短事务；执行期间由 Attempt 租约和 fence 决定谁有权更新。
2. **产物与状态的双写**：采用不可变文件先发布、数据库后引用，接受可清理孤立文件，避免数据库指向半成品。
3. **活着和有进展的区别**：心跳只说明控制路径可达，超时与进度停滞另行定义。
4. **资源所有权不等于资源已经释放**：数据库撤销租约并不能让旧 GPU 进程消失，必须隔离和确认清理。
5. **观测不依赖内存**：数据库历史提供证据；普通日志补充细节，trace 不承担恢复职责。

## 4. 错误协议

处理器返回的错误至少带 code、category、message、retryable_hint 和 details。`retryable_hint` 是提示，最终由领域策略决定；不能允许任意处理器把无效输入标可重试，从而无限消耗资源。

建议错误码：`INVALID_INPUT`、`PROCESSOR_VERSION_UNAVAILABLE`、`TRANSIENT_DEPENDENCY`、`EXECUTOR_EXITED`、`STEP_START_TIMEOUT`、`STEP_RUN_TIMEOUT`、`TASK_DEADLINE_EXCEEDED`、`LEASE_EXPIRED`、`GPU_OOM`、`ARTIFACT_INVALID`、`RESOURCE_CLEANUP_REQUIRED`、`STALE_ATTEMPT_REJECTED`。

上游需要看到可理解的摘要、是否可以恢复及下一步原因；堆栈、内部存储路径和凭据不直接暴露给普通页面。

## 5. 演示与公开部署的最小约束

本题可以只交公开源码，不必为了交付临时开放一个未受控的 GPU 服务。

- 演示故障配置由预置场景选择，不能让浏览器传任意命令、PID、文件路径或 Python 代码。
- 预置素材限定内容与尺寸，参数设上限；文件访问只允许 manifest 中的受控 file_key，防止路径穿越。
- 若以后支持任意 URL，需要单独解决 SSRF、超时、内容/大小校验与输入固化；P0 不支持。
- 若提供公网 URL，写接口至少需要演示访问令牌、并发与总任务数上限；只读样例可单独开放。Cookie 鉴权时还要处理 CSRF。
- 密钥放环境变量；仓库只放示例配置，数据库端口不直接暴露公网。错误和日志脱敏。
- Docker 只是部署和生命周期边界，不把可信本地处理器变成可执行不可信代码的沙箱。

这些措施服务于本题的可控演示，不扩展成完整账号、权限或安全平台。

## 6. 范围变化时如何取舍

时间紧时保留：异步接收、持久状态、Step/Attempt、租约/fence、重试、有效结果保留、最小查询、故障证据。界面只保留列表与详情即可。

优先推迟：精美交互、任意上传、真实模型、真实 GPU 采样、SSE、外部监控、动态 DAG。不能通过削掉 fence 或省略产物校验来“简化”，因为这会破坏题目的核心正确性。

如果 PostgreSQL 或 Linux 容器在目标机器不可用，应先重新确认部署方案与故障演示边界；不能未经评估把存储替换为内存、把资源锁替换为线程锁后仍声称满足相同恢复保证。
